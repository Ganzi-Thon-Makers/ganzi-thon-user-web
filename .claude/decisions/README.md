# 결정 기록

여러 기능에 반복 영향을 주고, 이후 구현의 선택지를 실제로 제한하는 구조·라이브러리·토큰·API 처리 규칙만 기록한다.

- 기록 전에 셋 다 맞는지 확인한다: 여러 후속 작업에 영향을 주는가, 합리적인 대안 사이에서 골랐는가, 바꾸려면 여러 파일을 함께 봐야 하는가.
- 기록 대상 예: 디렉터리·레이어 경계 변경, API client·상태관리·폼·테스트 전략 같은 반복 패턴, 라이브러리 추가·교체, 기존 규칙과 다른 예외 허용, 다시 논쟁할 가능성이 높은 trade-off.
- 기존 규칙을 그대로 따르는 CRUD 구현, 단순 화면 구현, 오타, 간격 조정, 좁은 설정값 변경, PR·커밋 설명으로 충분한 내용은 기록하지 않는다.
- 새 문서는 `records/NNN-short-title.md`로 쓰고 `template.md`를 따른다.
- 상태는 `proposed`, `accepted`, `superseded`, `rejected` 중 하나다.
- 결정을 보완할 때(같은 결정, 세부 조정)는 같은 문서의 "변경 기록"에 시점과 이유를 이어 쓴다.
- 결정을 뒤집을 때는 새 record를 만들고, 옛 기록은 지우지 않고 상태를 `superseded`로 바꾼 뒤 새 record를 링크한다.
- 한 기록에는 하나의 결정만 둔다.
- `accepted`는 "결정됨"이지 "구현됨"이 아니다. 아직 구현 전이면 본문 첫머리에 `> **구현 상태 (YYYY-MM-DD 확인): 미구현.**`을 남긴다.
