# issue

이슈 초안을 만든다. 사용자가 생성까지 명시적으로 요청하지 않으면 이슈를 직접 만들지 않는다.

## 작업 흐름

1. `.github/ISSUE_TEMPLATE/task.yml`과 `.claude/rules/git-workflow.md`를 읽는다. 폼 항목·타입 목록을 이 스킬에 복제하지 않고 항상 현재 파일을 기준으로 쓴다.
2. 사용자 설명과 필요하면 `git status --short`·`git diff --stat`으로 작업 범위를 파악한다.
3. 작업 타입을 폼의 선택지 중 하나로 고른다. 성능 개선은 `refactor`, 빌드·CI는 `chore`, 급한 운영 수정은 `hotfix`. 이 타입이 `<타입>/<이슈 번호>` 브랜치와 라벨이 된다(`issue-branch.yml`).
4. 폼 항목 순서대로 채운다.
   - **제목**: 무엇을 하는지 한글 명사형 한 줄(`[Feat]` 같은 접두사 없이). 예) `게시글 목록 무한 스크롤 추가`
   - **어떤 작업인가요**: 해결할 문제·추가할 기능 한두 문장. 버그면 재현 방법과 기대 동작.
   - **작업 내용**: `- [ ]` 체크박스 1~2개(큰 작업이면 묶음 단위로 3~5개까지).
   - **참고**: 관련 이슈·디자인 링크·문서. 없으면 비운다.
5. 확인되지 않은 일정·담당자·링크를 지어내지 않는다. 팀원이 열어볼 수 없는 출처(다른 프로젝트, 개인 저장소, 로컬 경로)는 쓰지 않는다.

## 생성 (요청받았을 때만)

사용자가 이슈 생성까지 요청하면 `gh auth status`로 확인한다. `gh`가 없거나 인증이 안 되어 있으면 만들지 않고 아래 출력만 준 뒤, GitHub에서 **작업 이슈** 폼으로 직접 만들라고 안내한다.

인증되어 있으면 폼과 같은 본문 형식으로 만든다. 워크플로우가 `### 작업 타입` 섹션에서 타입을 읽으므로 형식을 바꾸지 않는다.

```bash
gh issue create --title "<제목>" --body-file - <<'BODY'
### 작업 타입

<타입> - <폼 선택지 설명>

### 어떤 작업인가요

...

### 작업 내용

- [ ] ...

### 참고

...
BODY
```

## 출력 형식

웹 폼에 그대로 옮길 수 있게 항목별로 나눠 준다.

- `제목:` 한 줄
- `작업 타입:` 폼 선택지 그대로 (예: `chore - 설정·빌드·CI`)
- `어떤 작업인가요` / `작업 내용` / `참고`: 각각 하나의 Markdown 코드 블록
