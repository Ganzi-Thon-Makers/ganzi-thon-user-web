# 구현 품질 기준

## 판단 기준

- **가독성**: 한 파일에서 동시에 이해해야 할 맥락을 줄이고, 위에서 아래로 화면의 의도가 읽히게 한다.
- **예측 가능성**: 이름과 props만으로 어떤 상태·동작을 기대할지 드러낸다.
- **응집도**: 함께 바뀌는 마크업·데이터·상호작용·타입은 같은 feature 안에 가까이 둔다.
- **낮은 결합도**: 모양이 비슷하다는 이유만으로 서로 다른 화면의 변경 시점을 묶지 않는다.

## 구현 전

- 디자인·API 명세·기존 코드로 확인되는 사실과 아직 정해지지 않은 사항을 구분한다.
- 해석이 갈려도 사용자 흐름·API 계약·의존성에 영향이 없으면 가장 단순하고 되돌리기 쉬운 쪽을 고른다. 영향이 있으면 묻는다.
- 고른 가정과 버린 해석은 보고에 드러낸다. 요청보다 단순한 방법이 있으면 구현 전에 제안한다.
- 성공 기준은 화면·상태·테스트처럼 확인 가능한 결과로 정한다.
- 해결책이 문제보다 커졌다면 단순화한다.

## 공통화

- 일회성 중복은 허용한다. 함께 안 고치면 오류 위험이 큰 경우에만 공통화한다.
- 공통화 전에 묻는다: 화면마다 동작이 같은가? 문구·후속 동작이 같은가? 앞으로도 같이 바뀌는가?
- 공통 모듈을 바꿨을 때 영향받는 곳을 바로 나열할 수 없다면 과한 공통화다.
- 같은 책임의 유틸을 두 개 두지 않는다. 상위 호환 함수가 있으면 하위 함수를 지운다.

## 책임 나누기

- 함수와 핸들러는 한 가지 결과를 책임진다. 화면 이동·상태 변경처럼 다른 결과가 함께 일어나면 이름이나 호출 위치에서 각각 드러낸다.
- 한 파일이 화면 구성·데이터 변환·브라우저 제어·상태를 모두 맡기 시작하면 보이는 단위나 동작 단위로 나눈다.
- 같이 실행되지 않는 분기는 컴포넌트로 나눈다. 최상위에서 역할로 분기하고(`isOwner ? <OwnerActions /> : <ViewerActions />`), 하위는 한 시나리오만 맡는다.
- "페이지 전체 상태 훅"을 만들지 않는다. 검색 파라미터·서버 상태·폼 상태를 기능 단위 훅으로 나눈다. 예: `usePostSort()`는 `useSearchParams` + `router.replace`를 감싸 `[value, setValue] as const`를 반환한다.
- 폼은 응집 단위를 먼저 정한다. 필드가 독립 검증·재사용되면 필드 단위, 필드 간 의존·단계형이면 폼 전체 단위.
- props drilling은 먼저 composition(children·slot)으로, 그래도 깊으면 Context로 푼다. 역할을 드러내는 props까지 숨기지 않는다.

## 상태와 effect

- 서버 데이터를 `useEffect` + `useState`로 불러오지 않는다(`data-fetching.md`).
- 계산할 수 있는 값은 state로 복제하지 않고 렌더 중에 계산한다.
- prop이 바뀔 때 state를 리셋하려고 effect에서 setState하지 않는다. 부모에서 `key`를 바꾸거나 렌더 중 이전 값과 비교한다.
- 사용자 이벤트에서만 필요한 동작은 핸들러에 둔다. `useEffect`는 외부 시스템 구독·브라우저 API 동기화에만 쓰고 cleanup한다.
- 최신 콜백을 effect 의존성 없이 읽어야 하면 React 19의 `useEffectEvent`를 쓴다.
- Context·Provider는 떨어진 컴포넌트들이 같은 상태를 실제로 바꾸고 구독할 때만 도입한다. 상태 위치는 `data-fetching.md`의 "상태 위치" 표를 따른다.

## 자주 나는 버그

- 분기 후 `return`을 빠뜨려 `router.push`가 두 번 실행되지 않게 한다.
- 핵심 식별자는 falsy 가드를 한 곳에서 한다. `0`이나 `undefined`를 fallback 값으로 쓰지 않는다.
- 비동기 제출 중에는 버튼을 막는다(`mutation.isPending`).
- StrictMode의 mount → unmount → remount를 고려해, ref로 한 초기화는 cleanup에서 되돌린다.
- 가드를 "더 안전하게" 바꿀 때 정상 흐름을 막지 않는지 확인한다. 가드는 부정 케이스만 잡는다.
- 어색해 보이는 코드를 고치기 전에 다른 레이어에서 이미 방어하는지 확인한다.

## 변경 통제

- 모든 변경 줄은 요청과 직접 연결되어야 한다. 무관한 dead code·리팩터링 후보는 지우지 말고 보고만 한다.
- 새 상태·Provider·공통 컴포넌트는 기존 props·지역 상태·HTML/CSS로 안 되는 이유가 있을 때만 도입한다.
- 이번 변경으로 안 쓰이게 된 import·변수·함수만 같은 diff에서 정리한다.
- 주석 처리된 코드 블록, 디버그용 임시 코드를 남기지 않는다.

## 변경 전에 확인할 질문

- 처음 보는 사람이 이 파일이 화면에서 맡는 부분과 변경 이유를 빨리 알 수 있는가?
- 함께 확인해야 하는 화면·공통 코드 범위가 필요한 만큼으로 제한되는가?
- 작은 중복을 없애려다 서로 다른 화면의 수정 시점을 묶고 있지 않은가?
- 접근성·반응형·성능을 해치지 않고 더 단순하게 표현할 수 있는가?
