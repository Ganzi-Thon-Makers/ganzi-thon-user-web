# Git·커밋·PR

- 커밋·푸시·PR 생성은 사용자가 명시적으로 요청한 경우에만 실행한다.
- 컨벤션과 맞지 않는 상황이 생기면 팀과 논의한 뒤 이 문서와 실제 설정을 함께 고친다.

## 흐름

```text
이슈 → develop에서 <type>/<이슈 번호> 브랜치 (예: feat/5) → 구현·검증 → 커밋 → develop 대상 PR → 리뷰 → 병합
```

- 이슈 초안은 `/issue`, PR 초안은 `/pr`. 두 스킬은 사용자가 생성까지 요청하고 `gh auth status`가 통과할 때만 직접 만들고, 아니면 복사할 내용만 준다.
- `main`(배포)과 `develop`(통합)에는 직접 push하지 않고 PR로만 병합한다.
- 이슈·브랜치 type은 8개다: `feat`·`fix`·`hotfix`(긴급 수정, 커밋은 `fix:`)·`refactor`(perf 포함)·`style`·`test`·`docs`·`chore`(build·ci 포함). 라벨은 ✨ Feature·🐛 BugFix·🚨 Hotfix·♻️ Refactor·🎨 Style·✅ Test·📝 Docs·🔧 Chore로 붙고, 라벨은 GitHub 저장소에 미리 만들어 두었고, 이름을 바꾸면 `issue-branch.yml`·`pr-metadata.yml`의 `LABELS`도 같이 바꾼다. 커밋 type은 아래 표 전체를 쓴다.

## 커밋

[Udacity Git Commit Message Style Guide](https://udacity.github.io/git-styleguide/)를 바탕으로, scope를 쓰는 Conventional Commits로 맞춘다. `commitlint.config.mjs`가 검사한다.

```text
<type>(<scope>): <제목>   ← 필수. 변경 목적을 한글로, 50자 안팎(최대 100자), 마침표 없음

<본문>                    ← 선택. 무엇을·왜 바꿨는지 짧은 bullet 2~5줄

<푸터>                    ← 선택. Closes #12 / BREAKING CHANGE: 옮기는 방법
```

예) `feat(home): 홈 배너 추가`, `fix(shared): 토큰 만료 시 재요청 누락 수정`

| type       | 쓸 때                               |
| ---------- | ----------------------------------- |
| `feat`     | 새 사용자 기능·화면 동작            |
| `fix`      | 기존 동작·레이아웃·접근성 오류 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선        |
| `style`    | 동작 영향 없는 포맷                 |
| `test`     | 테스트 추가·수정                    |
| `docs`     | 문서·AI 작업 지침                   |
| `chore`    | 도구·설정·보조 작업                 |
| `ci`       | CI workflow                         |
| `build`    | 빌드·의존성                         |
| `perf`     | 성능 개선                           |
| `revert`   | 되돌리기                            |

- 제목은 완료 보고나 파일 나열이 아니라 변경 목적을 쓴다.
- 커밋 하나에는 리뷰·되돌리기가 가능한 책임 하나를 둔다. 리뷰어가 커밋 순서대로 따라갈 수 있게 나누고, 기능과 무관한 대량 포맷 변경은 따로 뺀다.
- 검증하지 않은 변경을 검증한 것처럼 쓰지 않는다.
- `Co-Authored-By`, `Generated by` 같은 AI 출처 문구를 커밋·PR에 넣지 않는다(팀 정책).
- 훅이 실패하면 원인을 고치고 다시 커밋한다. 훅을 건너뛰지 않는다.

## PR

- PR 제목은 커밋과 같은 형식을 권장한다. 병합 방식(squash·merge commit)은 팀이 정하지 않았으므로 어느 쪽을 전제로 쓰지 않는다.
- 본문은 `.github/pull_request_template.md`를 따른다: 무엇을 왜 바꿨는지, 실제 실행한 검증, UI 변경이면 스크린샷. 검증하지 못한 항목은 "리뷰어가 봐주면 좋은 부분"에 적는다.
- AI 지침·훅·lint·CI처럼 작업 방식을 바꾸는 변경은 진입점, 규칙 로딩, 자동화가 하는 일, 리뷰어가 확인할 결과를 함께 설명한다.
- 충돌은 작성자가 해결한다. CI 통과와 팀 리뷰 후 병합한다. CI 결과와 실제 병합 가능 여부(branch protection)는 따로 확인한다.

## 리뷰 체크리스트

- [ ] 브랜치명·커밋·PR 제목이 컨벤션을 따른다
- [ ] 이슈의 목표와 실제 변경 범위가 일치한다
- [ ] 이름이 직관적이고, 중복·미사용 코드·주석 처리된 코드가 없다
- [ ] 한 파일에 책임이 섞이지 않았다
- [ ] 실제로 생기는 로딩·빈 상태·에러를 처리했다
- [ ] 접근성(label, 의미 요소, focus)을 지켰다
- [ ] 실행한 검증과 공백이 PR에 적혀 있다
- [ ] UI 변경이면 스크린샷이 있다
