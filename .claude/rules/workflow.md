# 작업 흐름

1. 변경 성격(기능·수정·리팩터링·설정·문서)을 구분하고 `.claude/README.md` 표에서 필요한 규칙만 읽는다. 디자인 변경이면 Figma 노드를 함께 본다.
2. 작업 트리의 기존 변경과 관련 파일을 확인하고, 보호해야 할 기존 동작을 짧게 정한다.
3. 가장 작은 검증 가능한 성공 기준을 정한다(화면·상태·테스트·명령).
4. 필요한 파일만 고친다. 새 공용 경계·의존성·자동화가 필요하면 기존 패턴과 대안을 먼저 확인한다.
5. 검증(`verification.md`)을 실행하고, 검증 에이전트를 부른 뒤 결과와 공백을 보고한다.

## 변경 유형별로 더 볼 것

- **화면**: 디자인·명세를 먼저 확인한다. 상태 다섯 가지(로딩·빈 상태·에러·비활성·성공)와 좁은 화면을 확인한다. 공용 UI를 바꾸면 접근 가능한 이름·disabled·키보드 동작을 확인한다.
- **상호작용**: 필요한 가장 작은 클라이언트 경계를 찾고 cleanup·reduced motion·키보드·터치를 본다. browser API·storage·timer 의존은 테스트할 수 있게 작은 함수·훅으로 분리한다.
- **데이터 연동**: 엔드포인트·필드는 명세로 확인한다(`data-fetching.md`).
- **설정·CI**: 로컬 명령, lefthook, CI, 배포 build에 미치는 영향과 이벤트·권한·대상 브랜치를 함께 본다.
- **리팩터링**: 기능 변경과 섞지 않는다. 유지할 동작과 그걸 증명할 검증을 먼저 정한다. 새 레이어보다 삭제·이동·재사용을 우선하고, 큰 리팩터링은 단계(청소 → 품질 → 유틸 추출 → 구조)로 나눠 단계마다 검증한다.
- **문서**: 지금 존재하는 명령·디렉터리·자동화만 쓴다. 문서와 구현이 어긋나면 같은 변경에서 맞춘다.

## 무엇을 묻고 무엇을 기록하나

- 디자인·명세에 없는 사용자 흐름이나 비즈니스 규칙은 추가하기 전에 묻는다.
- 추상화는 감쌀 대상이 생겼을 때 만든다. 지금 필요 없으면 도입 조건만 결정 기록에 남긴다.
